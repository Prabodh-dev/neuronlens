# Decisions

Format: `A-<n>: <decision> — <reason>` (docs/APP_BUILD_GUIDE.md section 3.2).

## Web (Anand)

A-1: The web app uses Next.js 16 and React 19 with CSS modules and hand-drawn SVG and canvas charts, not Next 14, Tailwind, Zustand or Recharts — it was built and merged (PR #3) before the guide was published, it builds and passes the core path, and switching now adds risk with no visible gain.
A-2: Black-and-white theme with the Geist font instead of the guide's lime accent and system fonts — chosen by the web owner; `next/font` downloads Geist once at build time and serves it from the app, so the running app needs no network.
A-3: The API address is set with `NEXT_PUBLIC_API_BASE`, which includes `/api/v1` (default `http://localhost:8000/api/v1`) — this matches `web/.env.example`, already on main.
A-4: Steering strength runs from 0 to 3 in steps of 0.25, default 0.5 on the Steer page and in the Microscope (the guide says 0 to 10, default 4) — the API contract caps `strength` at 3 (`SteerRequest`, `le=3`), and the contract outranks the guide; at 0.5 the checked features change the text, and some features drift or loop from about 1.0 (#13 and #3587 in the GPU runs).
A-5: `/inspect` requests time out after 30 s (reads 10 s, `/steer` 60 s, as in the guide) — the guide does not list inspect, and it runs the model, so it gets more than a read.
A-6: Percent values below 1 keep two significant digits, otherwise one decimal — the real `dead_pct` is 0.0081 (1 of 12,288 features), which one decimal would show as a misleading 0.0% and three decimals as 0.008%.
A-7: The "sample data" marks come from `is_synthetic`, and the "simulated" marks on Inspect and Steer come from `mode` — so real data served in mock mode is never labelled as fake.
A-8: Tokens are shown exactly as stored, never trimmed, with `↵`, `⇥` and `␠` for invisible characters; leading spaces stay spaces — section 10.3 and gotcha 5. An empty token shows as a small, clickable `·` chip instead of `∅` — after the byte-stream decoding fix (PR #4) the leading byte-pieces of characters such as ’ arrive as empty strings, and `·` reads as a quiet joiner rather than an error.
A-9: Two extra screens: a landing page at `/` and a Microscope at `/microscope` that shows every feature as a square tile in square rings by density rank (most frequent in the centre); clicking a tile or typing its number flies into it and opens it — the positions carry no claim about which features are near each other. The Microscope keeps this density-ring layout. W7 (a 2D map of the features) is dropped from the demo, and no endpoint is proposed for it. Reason: the check result. The nearest points to #13, #7 and #1863 did not match those features, so a map layout would imply neighbours that the data does not support. A map built from co-fire data is out of scope for this project; a map could be reconsidered if a method passes the same neighbour check.
A-10: Example tokens carry a `title` and `aria-label` with their activation, but are not tab stops — a detail page holds about 2,000 tokens, which would make keyboard navigation unusable.
A-11: Headings and helper text not covered by the copy deck are kept short; every copy-deck key in use is taken word for word from `web/src/lib/copy.ts`.
A-12: The Microscope asks `/inspect` for 20 features per token (the API maximum) so the field shows a fuller picture of each token; the Inspect page defaults to 5.
A-13: The header's status pill shows only the server state (Mock, Live, Sample data, Offline); the model chip (`gpt2 · L8 · 12,288 · k=32`) unfolds inside it on hover or keyboard focus and is always in its `aria-label`, and the header has no "Open microscope" button (Microscope is the first link) — section 10.3 lists the chip on its own; folding it keeps the bar short while the same facts stay one hover away.
A-14: The landing page opens with a self-playing tour of the real data (all features, one `/inspect` sentence, three named features, one steering run, `ce_recovered`) that loops and can be paused or jumped by chapter — the guide has no landing screen (see A-9); it starts paused for people who ask for reduced motion. The steering chapter is the demo's headline run, #3446 up 0.5 on "The band walked on stage and" with seed 42, through `/steer/check`, so it shows both texts and the activation check (0.00 to 12.44 on the GPU); it is live on the model in real mode and labelled "simulated" in mock mode, and the chapter is left out if the call fails. Each feature is drawn as a small neuron (cell body, dendrites, axon) and the visited one as a large neuron with signals running through it; the shape is an illustration with no claim about the model, while which features fire, and how strongly, is the real data.
A-15: On the landing page the header and its banner slide out of the way while the tour fills the screen, and come back as soon as you scroll, move the mouse to the top edge, or tab into them; the tour shows the same banner text (mock, sample data or offline) at its top edge in the meantime, so simulated results are never on screen without it (gotcha 14).
A-16: `NEXT_PUBLIC_MODEL_ONLY=1` (off by default) makes every page wait for `/health` and show a "Not running on the model" screen when the server is in mock mode, reads a synthetic database, or answers `MODEL_NOT_LOADED` to a one-token `/inspect` — the demo machine must never show simulated or sample results, while the other machines keep using mock mode as section 11.3 says.
A-17: The separate Limits box (X5) was removed from the landing and Metrics pages at the web owner's request — the honest limits stay where the results are: each Steer page check (X1 to X4) shows its own limit under its result, and the footer keeps `note.limit` on every page.
A-18: The Phase 4 checks live on the Steer page: the main Run calls `/steer/compare` (X3) and `/steer/check` (X1) together, and two more tabs hold Every strength (X2) and Prompt only (X4) — one place to test a feature. Two "Saved runs" buttons rerun the GPU-checked demo runs live, #3446 and #13, both up 0.5 with seed 42; #1863 stays a recorded example only, because it depends on the prompt and touches a hot-button topic. Seed and strength are shown next to every steered text. The raw percent of changed tokens is never shown (docs/phase4-ml-api.md says it overstates the effect), and saved examples say "changed words" without a percentage for the same reason.
A-19: X6 and X7 live on the Inspect page as two more tabs next to "Each token" ("By sentence", "Two texts"), and W4 is a "Fired on the same tokens" panel on the feature page under the next-word effect — each sits where its input already is. Strength bars use `relative_to_max`, the order stays the server's (raw activation); the "word-piece features often dominate" limit is shown under the X6 and X7 results, since the separate Limits box was removed (A-17). Co-fire wording follows docs/features/W4.md: the sample size and counts come from the API, never "related" or "similar", a partner is linked only when `in_dictionary` is true, and the panel is hidden when `available` is false. The `max_density` filter is a "Hide very common features" checkbox on both tabs, off by default as on the server; on, it sends 0.01, which hides the features that fire on more than 1% of tokens. Some named features are hidden too (for example "the – noun phrase start"); the note under the result says that features above 1% were hidden (the API does not return how many).
A-20: W5 is a Combine tab on the Steer page (`POST /steer/multi`), using the prompt, seed and length on the left: two or three features, each turned up at its own strength (0.25 to 3, default 0.5; amplify only), always with `with_single_controls: true`. Each feature run alone is shown only as its activation number beside the combined one, never its text (Prabodh; server/README.md: those texts can be harsh). The recorded pair (#4280 + #9530, up 0.5, seed 42) is one click and carries "Found by search, depends on the prompt"; that label and the held-out caveat appear only for that pair. A degenerate combined text gets the sweep's warning style (the solid "Breaks down" tag, the reason, the hatched background). The tab shows only when the server's /openapi.json lists `/steer/multi`, so an older server never shows a broken tab. Wording: "shows which concepts were active", never "related" or "fixes".
A-21: W8 lives in the Features page search box as "Your words" next to "Name", since it answers the same question (which features?) from a different input. By name the list still follows the box as you type; by your words it runs on Enter, because it runs the model. It always sends `max_density: 0.01` with no toggle (Prabodh; server/README.md) and the heading reads "Features that fired most on your words". The Auto-Lab fillers (web/public/autolab-fillers/<model id>.json) are dropped here too, so the list still shows 10 and the note under it says how many were left out: in the recorded real search for "court law", #1375 (more – text navigation) and #5023 (off-) were in the top 5 on the word "court", and GPT-2 reads left to right, so they have the same reading on "court" in "court ruling". The option shows only when the server's /openapi.json lists `/features/search`. On Inspect, "Rank by" (Strongest, Closest to its own peak) sends X6/X7's `sort`, default Strongest as on the server; the note under the result says how it was ranked.
A-22: S5 shareable links use URL parameters only (no server storage), built and read in web/src/lib/share.ts. The feature page's existing "Copy link" now copies `/features/{id}?run=…`; a live Steer result gets its own "Copy link" with feature, mode, strength (amplify only), seed, length and prompt. Opening a steering link fills in the form and reruns `/steer/compare` and `/steer/check`, which reproduces the result because generation is seeded. Every link carries the server's `run_id`; when it differs from the server's, a note says the result can differ. Running something new drops the link's parameters from the address bar, so a reload never brings back an old result. Saved runs get no link, since their length is not recorded.
A-23: Auto-Lab has its own page in the navbar (`/autolab`, web/src/app/autolab/), not a tab on the Steer page (Anand: one place for it). It runs only existing endpoints, with the model calls one at a time: the search (W8, the goal's words with a leading space so the first word gets its mid-sentence token, `max_density` 0.01, top 8, the fillers in web/public/autolab-fillers/<model id>.json dropped, the first 5 kept), each candidate's name and top example from the database (all at once, beside the sweeps, so they never hold up the first one), then for each candidate the Every strength sweep (X2, seed 42, 60 tokens) with `with_activations` for its readings; a server without that flag gets the activation check (X1) per strength instead. Strength 0 is shown as an "unsteered" control column, not tagged. A cell is ✓ when the rise is at least 3.0 and the steered reading at least 2x the unsteered one with the loop tag off, ⚠ when the loop tag is on, ✗ otherwise (`WORKED` in web/src/lib/autolab.ts, the same numbers as server/scripts/autolab_check.py). The verdict follows rule v2 exactly as the script (a ✓ is stable when a neighbouring strength is also ✓; only features with a stable ✓ can be recommended; the most ✓ cells wins, a tie goes to the higher rise, at the lowest stable strength; otherwise "Worked at one strength only, not reliable" or "Nothing worked"), and was checked against the script on all 18 recorded laptop runs. Goal buttons are the six that shipped from the laptop test (Music, Courts and law, Space, Food, Weather, Sports), with the recorded search words, in one presets file. A typed goal is 1 to 3 words, checked against one blocklist file, and the run stops before any sweep when the model splits the words into more than 2 pieces each (the search's query tokens divided by the words typed; random letters give 3 to 4, real words 1 to 1.5) or when fewer than 3 features are left after the fillers are dropped (Prabodh). Candidates are "features that fired on these words", shown with a top example. A mock or sample-data server runs it labelled Simulated, like every other tab, and NEXT_PUBLIC_MODEL_ONLY=1 keeps simulated numbers off the demo machine; all text stays behind "Show text". The grid fills in live, cell by cell from left to right, and the finished table plays one slow wave, row by row, once it is on screen (it waits while scrolled away); every cell and bar opens an inspector with the test's readings, which parts of the rule it met, and why the recommendation was picked. It keeps the site's black and white: tags differ by brightness and texture (worked bright white, breaks down hatched with a dashed edge, no effect dim grey), neighbouring ✓ are joined by a line, the accent is the grey-to-white heat ramp, and the goal buttons use single-colour symbols. Feature card: docs/features/AutoLab.md.
A-24: The stretch window was narrowed to Auto-Lab. S5 and Auto-Lab are done; S1, S2, S3 and S4 were not built, and W7 was not built (A-9).
A-26: A second model (experimental, next to GPT-2) runs in the same app through a model chooser, not a second app: each model is its own server with its own database, and the pages only change which server they call (web/src/lib/models.ts). The model is `?model=<id>` in the address, read once per page load (choosing another reloads the page, so two servers' answers never mix); no parameter means the default model, so existing links and the demo are unchanged. The chooser is the status pill's menu in the top bar and shows only when more than one server answers /health. Names, layers and sizes come from /health, so no model name is written in the app. Everything picked or recorded on GPT-2 is keyed by model id: the home page and tour picks, the Steer and Combine one-click runs, Auto-Lab's prompts, goals and time estimate, and the filler lists (public/autolab-fillers/<id>.json, copied from demo/autolab_fillers_<id>.json by web/scripts/copy-fillers.mjs). A model without them gets live runs and empty states, never another model's numbers. The second model carries an "experimental" tag, and Auto-Lab says its ✓ thresholds were tuned on another model's runs. Feature card: docs/features/ModelChooser.md.
